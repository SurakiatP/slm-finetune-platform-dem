# Runbook — Backup and restore

This is gap-analysis item 9: until now there was no backup of anything on
the pasaflow box — a disk failure or a bad `docker compose down -v` would
have taken the entire platform (every project, dataset, trained model,
MLflow run) with it, with no way back. Three scripts close that gap:
`scripts/backup.sh`, `scripts/restore.sh`, `scripts/verify_restore.sh`.
This runbook documents the contract those scripts implement — the exact
directory layout, flags, and required env vars — not their internals.

Same access constraints as every other runbook here: wetty only, no SSH
(port 22 filtered), rootless docker running as uid 1001 with no sudo, and
all persistent data (including backups) lives on `~/drive`, the
customer-mounted 5 TB external HDD (`scripts/deploy_pasaflow_vm.sh`'s
Phase 1). A backup set is a plain directory under `$BACKUP_ROOT` (default
`~/drive/slm-backups/<UTC-YYYYmmdd-HHMMSS>/`):

```
db/globals.sql          # pg_dumpall --globals-only (roles, incl. password hashes)
db/slm.dump              # pg_dump -Fc of the app database
db/mlflow.dump            # pg_dump -Fc of the mlflow database
db/rowcounts.tsv          # per-table row counts at dump time
minio/datasets/           # mirror of the datasets bucket
minio/models/             # mirror of the models bucket
minio/mlflow/             # mirror of the mlflow artifact bucket
minio/objectcounts.tsv    # per-bucket object counts at mirror time
manifest.tsv              # file list + checksums for everything above
backup.log                # this run's transcript (chmod 600)
BACKUP_COMPLETE           # marker file holding the UTC completion timestamp, written LAST
```

`BACKUP_COMPLETE` being written last is the whole contract: a set that
doesn't have it was interrupted mid-run (box rebooted, disk filled, `set
-e` tripped) and must never be treated as restorable or counted toward
retention. Everything below assumes that invariant.

## Full-box DR procedure

Scenario: the pasaflow box is gone (disk died, VM lost) and you're
starting over on a fresh box with the backup HDD (or a copy of it)
attached.

1. **Stand up the stack** — run `scripts/deploy_pasaflow_vm.sh` as
   normal (see the `deploy-slm-vm` skill). This gets you a fresh
   `~/drive/slm-data/{postgres,redis,minio,...}`, migrations applied,
   and all 11 services running with day-one credentials.
2. **Stop the app services, leave postgres + minio up** — restore needs
   somewhere to write, but nothing should be reading half-restored data
   or racing the restore with new writes:
   ```bash
   docker compose --profile tunnel stop api worker worker-cpu mlflow
   ```
   (`edge` and `cloudflared` can stay up or down — they don't touch the
   DB or object store directly. `redis` is untouched either way; see
   "Exclusions" below for why it's never restored.)
3. **Point RESTORE_* at the LIVE containers, not throwaway ones** — this
   is the one case where `restore.sh` is deliberately told to target the
   real thing, gated by the same live-target refusal every other case
   relies on:
   ```bash
   export RESTORE_PG_CONTAINER=slm-postgres
   export RESTORE_MINIO_URL=http://minio:9000
   export RESTORE_MC_NETWORK=slm-platform_slm-net
   export RESTORE_MINIO_USER="$(grep '^MINIO_ROOT_USER=' .env | cut -d= -f2-)"
   export RESTORE_MINIO_PASSWORD="$(grep '^MINIO_ROOT_PASSWORD=' .env | cut -d= -f2-)"
   export RESTORE_ALLOW_LIVE=1
   ```
   `slm-postgres` is the fixed `container_name:` from
   `docker-compose.yml` — not a compose service name, not a
   project-prefixed autogenerated name. `RESTORE_PG_CONTAINER` is a
   `docker exec` target, so it needs no published port at all.

   MinIO is reached the other way round: `restore.sh` runs `mc` in a
   throwaway container attached to `RESTORE_MC_NETWORK`, so
   `RESTORE_MINIO_URL` uses the **compose service name** `minio:9000`,
   resolved by docker's embedded DNS on that network. The network is
   `slm-platform_slm-net` — compose prefixes the `slm-net` network with
   the `name: slm-platform` project name from `docker-compose.yml`.
   Confirm before running, since a wrong name fails the `mc` container
   immediately:
   ```bash
   docker network ls --filter name=slm-net --format '{{.Name}}'
   ```

   **Why not `--network host` + `localhost:9000`?** Docker on this box
   is rootless (uid 1001). A container started with `--network host`
   joins RootlessKit's *child* network namespace, but ports published as
   `127.0.0.1:<port>` are listening in the *parent* (real host)
   namespace — so a loopback address is simply unreachable from inside
   the `mc` container, and every bucket operation fails to connect.
   Container-name DNS on a shared docker network is the only channel
   that works here, which is also why `backup.sh` mirrors via
   `docker compose run` on the `minio-init` service rather than a
   host-network container. Do not "simplify" this back to `localhost`.
4. **Restore**:
   ```bash
   ./scripts/restore.sh ~/drive/slm-backups/<UTC-timestamp>/
   ```
5. **Verify**:
   ```bash
   ./scripts/verify_restore.sh ~/drive/slm-backups/<UTC-timestamp>/
   ```
   Non-zero exit means stop here and investigate — do not restart
   services against data verify_restore.sh flagged as bad.
6. **Restart the app services**:
   ```bash
   docker compose --profile tunnel up -d --force-recreate api worker worker-cpu mlflow
   ```
   (`--force-recreate`, not `restart` — same reasoning as
   `secret_rotation.md`'s Postgres section: these were stopped, not just
   restarted, and should pick up a clean process against the now-restored
   DB rather than any cached state.)

**Post-restore note — expect job_reconcile to fail every in-flight job.**
Redis (queue state, task progress, circuit-breaker state) is not part of
the backup — see "Exclusions" below — so nothing restored knows about
whatever training/SDG/export/evaluation jobs were mid-flight at backup
time. `api/services/job_reconcile.py`'s orphan sweep runs automatically
and will mark every such job `FAILED` with `"no worker is executing this
job"` shortly after the services come back up. That is expected, correct
behavior, not a bug in the restore — those jobs' actual progress was
never durable in the first place. See
`docs/adr/ADR-010-cpu-gpu-queue-split-and-quotas.md` for why job state is
derived from the DB and swept for orphans every 5 minutes rather than
trusted to survive in Redis. Re-launch them from the UI/API as new jobs.

## Partial restore

For pulling one DB or one bucket back — a bad migration, an accidentally
truncated table, a corrupted object — without touching anything else.

```bash
./scripts/restore.sh <set-dir> --db slm                  # app DB only
./scripts/restore.sh <set-dir> --db mlflow                # mlflow DB only
./scripts/restore.sh <set-dir> --db all --skip-globals    # both DBs, skip role/password restore
./scripts/restore.sh <set-dir> --bucket datasets           # one bucket
./scripts/restore.sh <set-dir> --bucket models
./scripts/restore.sh <set-dir> --bucket mlflow
./scripts/restore.sh <set-dir> --bucket all                 # all three buckets
```

`--skip-globals` matters whenever you're restoring into anything other
than a from-scratch container: `db/globals.sql` recreates roles
(including password hashes) and will happily clobber a role's current
password with whatever it was at backup time — fine on a fresh box in
the full-DR case above, almost never what you want for a partial restore
against an already-running Postgres.

**Rehearse against throwaway containers first — never point a partial
restore at a live target without `RESTORE_ALLOW_LIVE=1`, and don't set
that flag until you mean it.** Stand up a disposable network plus a
Postgres/MinIO pair on it. They never touch the live stack's network,
and no host ports are published at all — `restore.sh` reaches Postgres
by `docker exec` and MinIO by container-name DNS, so nothing needs to
be exposed on the host (see the DR section's rootless-networking note
for why publishing a loopback port would not have helped anyway):

```bash
docker network create restore-net

docker run -d --name restore-pg --network restore-net \
  -e POSTGRES_USER=slm -e POSTGRES_PASSWORD=<throwaway> -e POSTGRES_DB=slm \
  postgres:16-alpine

docker run -d --name restore-minio --network restore-net \
  -e MINIO_ROOT_USER=<throwaway> -e MINIO_ROOT_PASSWORD=<throwaway> \
  minio/minio server /data
```

Then point `restore.sh` at them instead of the live containers:

```bash
export RESTORE_PG_CONTAINER=restore-pg
export RESTORE_MINIO_URL=http://restore-minio:9000
export RESTORE_MC_NETWORK=restore-net
export RESTORE_MINIO_USER=<throwaway>
export RESTORE_MINIO_PASSWORD=<throwaway>
# RESTORE_ALLOW_LIVE intentionally left unset — restore.sh refuses to
# target anything it thinks is the live stack without it, and these
# throwaway containers aren't it anyway.
```

`verify_restore.sh` takes the same five exports, so run it against the
rehearsal target straight afterwards:

```bash
./scripts/verify_restore.sh <set-dir>
```

Tear it all down once done — the containers hold real dumped data
(including the password hashes in `globals.sql`) for as long as they're
up:

```bash
docker rm -f restore-pg restore-minio && docker network rm restore-net
```

## Consistency gap

Backup takes no lock and nothing is quiesced — the app, workers, and
MLflow all keep running while `backup.sh` executes. That's a deliberate
tradeoff (a maintenance window on a single-box platform is a real cost;
a few seconds of skew in a point-in-time backup isn't), but it means the
DB dumps and the bucket mirrors are not one atomic snapshot — they run
sequentially, DB dumps first, then bucket mirrors.

That ordering is what keeps the gap one-directional. Workers upload the
MinIO object *before* committing the row that references it (item 13's
contract) — so during the window between the DB dump and the bucket
mirror, at worst a worker finishes a job and uploads+commits something
new. The DB dump, taken first, can't yet reference that new object; the
bucket mirror, taken after, picks it up anyway. Net effect:

- **A DB row referencing a missing object — cannot happen from backup
  timing.** By the time any row exists that references an object, the
  object was already durably written (item 13's upload-before-commit
  order), and the bucket mirror always runs after the DB dump, so it can
  only ever have *more* objects than the dump references, never fewer.
- **An object in the bucket mirror with no referencing DB row —
  can happen, and is harmless.** It's just an orphan blob nobody points
  to; nothing dereferences it, nothing breaks.

`verify_restore.sh`'s dangling-URI sweep (checking every DB-referenced
URI resolves to an object that actually exists post-restore) is what
proves this holds on any given backup set — not an assumption to trust
blindly. If that sweep ever finds a dangling reference, treat it as a
real bug in the upload-before-commit ordering, not as "expected backup
skew."

## Retention and scheduling

`backup.sh` keeps the newest `BACKUP_RETAIN` (default 7) **complete**
sets — anything without a `BACKUP_COMPLETE` marker is never touched by
retention pruning, complete or not, recent or not. That's intentional:
an incomplete set is exactly the evidence you'd want if backups start
silently failing, and auto-deleting it would erase the trail. Cleaning
up abandoned incomplete sets is a manual decision, not something
retention does for you.

Scheduled via the uid-1001 user's own crontab — no sudo, no system
crontab, no systemd timer (none of those are available to this user on
this box):

```
0 2 * * * cd $HOME/drive/slm-platform && /usr/bin/env bash scripts/backup.sh >> $HOME/drive/slm-backup-cron.log 2>&1
```

Install it with `crontab -e` (opens the uid-1001 user's own crontab in
`$EDITOR`), paste the line above, save and exit. Verify it's registered:

```bash
crontab -l | grep backup.sh
```

02:00 local is a first guess at a low-traffic window on this box — there
is no SLA driving the exact hour, adjust if a training run is regularly
found overlapping it.

## Known gaps

1. **No offsite copy.** Every backup set lives on `~/drive`, the same
   physical HDD as the primary data it's backing up. A disk failure or
   loss of the box takes the backups down with everything else — this
   procedure protects against logical corruption (a bad migration, a
   fat-fingered delete) and against needing to rebuild a box from
   scratch onto the *same* disk, not against losing that disk itself.
   Closing this needs a second target (another box, cloud object
   storage) and its own credentials — deliberately out of scope for this
   round.
2. **BackupStale alerting deferred.** If the cron job above starts
   silently failing (disk full, script error, box down at 2am), nothing
   currently notices — Prometheus has no visibility into backup
   freshness at all. The follow-up (mount a timestamp from the backup
   job into something the `api` container can read, export it as an
   `slm_backup_age` gauge, add an alert rule alongside the six in
   `docs/runbooks/metrics.md`) is recorded in `TASK_TRACKER.md`, not done
   here.
3. **Backups are unencrypted, by decision, not oversight.** An
   encryption key stored on the same disk as the data it protects adds
   no real protection against the actual threat model here (disk/box
   loss) — anyone with the key has the data anyway, and anyone without
   the disk has neither. The compensating control is access control, not
   encryption: every backup set directory is `chmod 700`, and
   `db/globals.sql` contains Postgres role password hashes, so treat the
   whole of `$BACKUP_ROOT` as sensitive — same handling as `.env` in
   `docs/runbooks/secret_rotation.md`.

## Exclusions

Three things on this box are deliberately never backed up:

- **Redis.** Purely transient state — Celery queue contents, task
  progress, the OpenRouter circuit-breaker state (ADR-010). Restoring a
  stale Redis snapshot would resurrect in-flight job state that no
  longer matches reality (a "running" job whose worker process is long
  gone) rather than actually recovering anything; `job_reconcile`'s
  orphan sweep exists precisely to clean up exactly that aftermath on
  every boot, so there's nothing for a Redis backup to usefully protect.
- **Ollama's model directory.** Fully re-derivable: base models re-pull
  from the Ollama registry (`scripts/deploy_pasaflow_vm.sh`'s Phase 6.5),
  and fine-tuned models re-register from their GGUF artifact, which
  *is* backed up (`minio/models/`). Backing up multi-GB model blobs a
  second time on top of that would just be spending HDD space to
  duplicate data already covered another way.
- **The Hugging Face cache** (`~/drive/slm-data/hf-cache`). Re-downloadable
  from HF on demand — it exists purely to avoid re-fetching base model
  weights/tokenizers on every training run, not as a source of truth for
  anything. Same reasoning as the Ollama dir: backing it up would trade
  HDD space for zero actual recovery benefit.
