Tech Stack — SLM Fine-Tuning Platform

Backend-only PoC สำหรับ Automated Small Language Model Fine-Tuning. หน้านี้สรุปทุก component ที่ใช้จริงในระบบและบทบาทของมัน
Python 3.11+ Docker Compose Models ≤ 3B (QLoRA 4-bit) No frontend / no auth Source: docs/architecture/TECH_STACK.md

Workflow ระบบ End-to-End พร้อม Tech Stack ที่ใช้แต่ละขั้น

เริ่มจาก Create Project → SDG → Training → Export → Serve → Evaluation → LLM as Judge. แต่ละ step ระบุว่าใช้ tech อะไรบ้าง โดยจัด สีตามหมวด ดังนี้:

Legend: api/web infra async / queue ml / training external api metrics / eval
1
Create Project POST /api/v1/projects SYNC · 201

User กำหนด task_type (classification / tool_calling / qa) ซึ่ง lock ไว้ตลอดอายุของ project. ทุก dataset / training / evaluation ภายใน project ต้องเป็น task_type เดียวกัน. เป็น CRUD ปกติ ไม่มี GPU, ไม่มี Celery.

FastAPI Pydantic v2 SQLAlchemy 2.0 (async) PostgreSQL 16 Alembic pydantic-settings
↓
2
Synthetic Data Generation (SDG) + Holdout Split POST /api/v1/datasets/generate ASYNC · 202 + WS

Celery worker ดึง teacher LLM (default = Claude 3.5 Sonnet) ผ่าน OpenRouter generate training rows ทีละ batch → Pydantic validate ตาม task type → SHA-1 dedup → stratified split → save train JSONL (parent) + holdout JSONL (child) ลง MinIO. Progress publish ลง Redis pub/sub แล้ว WebSocket forward ให้ FE realtime.

Celery 5.4 Redis (broker + pub/sub) tenacity (retry 429/timeout) OpenRouter openai SDK 1.58 Pydantic validators MinIO (S3) WebSocket (FastAPI)

3
Training (Manual / HPO) — QLoRA 4-bit fine-tune POST /api/v1/trainings ASYNC · 202 + WS · GPU

Celery worker (NVIDIA runtime, 1 GPU) โหลด base model แบบ 4-bit ผ่าน Unsloth (เร็วกว่า HF Trainer ~2x, VRAM น้อยกว่า) → เพิ่ม LoRA adapter (peft) → train ผ่าน TRL SFTTrainer. Mode hpo ใช้ Optuna ค้น hyperparameters — แต่ละ trial = nested MLflow run. Metrics + params log ลง MLflow, adapter save ลง MinIO. Cleanup GPU ใน finally เสมอ (ADR-002).

↓
4
Export GGUF + Register Ollama POST /api/v1/models/{id}/export ASYNC · 202 + WS

Merge LoRA adapter เข้า base ด้วย peft.merge_and_unload() → quantize เป็น GGUF (default q4_k_m, ~770 MB สำหรับ 1B) ผ่าน llama-quantize binary ที่ฝังใน worker image → upload GGUF ขึ้น MinIO → เขียน Modelfile → ollama create slm/<id8>. นอกจากนี้ยัง auto-pull base model มาด้วย (best-effort) เพื่อให้ A/B compare ทำได้ทันทีโดยไม่ต้อง SSH.

Celery peft.merge_and_unload llama-quantize Ollama MinIO httpx (Ollama HTTP API)
↓
5
Serve / Inference (OpenAI-compatible) POST /api/v1/inference/chat/completions SYNC · 200

FastAPI resolve UUID หรือ Ollama tag (slm/<id8> / llama3.2:1b) แล้ว proxy แบบ async ไปยัง Ollama /v1/chat/completions. Response shape เหมือน OpenAI ทุกอย่าง — client lib ตัวไหนที่รองรับ base_url override ก็ใช้ได้. รองรับทั้ง fine-tuned + base ในเวลาเดียวกัน → A/B compare ใน playground. (Streaming reject ที่ 400 — out of PoC scope)

FastAPI (async proxy) httpx Ollama daemon GGUF runtime
↓
6
Evaluation (Quantitative Metrics) POST /api/v1/evaluations ASYNC · 202 + WS

Celery worker loop ทุก row ใน holdout child dataset → call Ollama → compute metric ตาม task_type: classification ใช้ sklearn (accuracy, macro-F1, confusion matrix), tool_calling ใช้ stdlib (json_validity, name_accuracy, arg_accuracy), QA ใช้ rouge_score + sacrebleu. ผลลัพธ์ metrics_json save ลง EvaluationRun row. API guard: ถ้า task_type ของ dataset ไม่ตรงกับ artifact → 400.

Celery Ollama (predictions) scikit-learn 1.6 rouge-score sacrebleu evaluate (HF) Pydantic (metric schemas)
↓
7
LLM as Judge (Qualitative Scoring) include_llm_judge=true ใน /evaluations ASYNC · embedded in step 6

Step สุดท้ายที่ทำให้ระบบ "ตัดสินคุณภาพ" output ที่ ตัวเลขล้วนวัดไม่ได้ (โดยเฉพาะ QA และ open-ended). ส่งทั้ง question, expected, predicted ของแต่ละ row ไปให้ teacher LLM พร้อม rubric 1-5 และบังคับ response_format: json_object → parse score → เฉลี่ยทุก row → เก็บเป็น llm_judge_score ใน metrics_json ของ EvaluationRun. Rows ที่ parse fail จะถูก skip และนับใน skipped. ผลคือ judge score ที่ เทียบเทียบกันได้ระหว่าง run และเอาไปเลือก best artifact ได้.

Celery (in eval task) OpenRouter (teacher = Claude 3.5) openai SDK tenacity deepeval 2.0 Pydantic (rubric schema)

ⓘ Step 1, 5 เป็น sync — HTTP ปกติ. Step 2, 3, 4, 6 (รวม 7) เป็น async — return 202 ทันที + WebSocket ส่ง progress. WebSocket pattern เดียวกันหมด: subscribe /ws/jobs/{job_id} → รับ *_progress events → รอ completed หรือ failed → FE close socket เอง.

1. เป้าหมายของระบบ & ภาพรวม flow

รับ task description (จากผู้ใช้) → สร้าง synthetic data → fine-tune SLM ขนาด ≤ 3B แบบ QLoRA → track ทุก experiment ลง MLflow → export GGUF → serve ผ่าน Ollama (OpenAI-compatible). ทั้งหมดทำงานบน 1 node (single host) โดยใช้ GPU 1 ใบ.

User → FastAPI ——▸ PostgreSQL (state) │ ├──▸ Celery (Redis broker) ——▸ Worker (GPU) │ │ │ ├─ ai_engine.data_gen (OpenRouter) │ ├─ ai_engine.training (Unsloth + QLoRA) │ ├─ ai_engine.hpo (Optuna) │ └─ ai_engine.evaluation (metrics + LLM judge) │ ├──▸ MinIO (datasets, model artifacts) ├──▸ MLflow (params, metrics, model registry) └──▸ Redis Pub/Sub ——▸ WebSocket /ws/jobs/{id} ↑ └─ Frontend (teammate, separate) Trained model ——▸ Ollama (GGUF) ——▸ OpenAI-compatible inference API

Hexagonal discipline (สำคัญ)

  • Domain (ไม่พึ่ง infra): ai_engine/ — data_gen, training, hpo, evaluation
  • Application (orchestration): workers/tasks/ — Celery tasks ที่ประกอบ domain + persistence + progress
  • Adapters (HTTP / DB / queue): api/ — FastAPI routers, schemas, ORMs, services

กฎ: ai_engine ห้าม import จาก api/ หรือ workers/. Adapters import เข้าด้านใน (inward) เท่านั้น.

  • Read status / metadata
  • Inference (chat/completions)

  • SDG generation
  • Manual training
  • HPO training
  • Evaluation runs
  • Model export (GGUF)

7. ML Training (Unsloth + QLoRA + MLflow)

Stack ที่ทำให้ fine-tune model ขนาด 1-3B บน RTX 3060 (12GB) ได้จริง โดยใช้ 4-bit quantization + LoRA adapter (parameter-efficient).

LibraryMin Versionหน้าที่
torch2.5.1Tensor + CUDA backend. ทุก library ML ข้างล่างพึ่ง torch.
unsloth2024.12.4Hero library. Optimized kernels ทำให้ fine-tune เร็วกว่า HF Trainer มาตรฐาน ~2x และใช้ VRAM น้อยกว่า. รองรับ QLoRA 4-bit ตรงๆ.
transformers4.47.0HF model + tokenizer + Trainer base classes ที่ Unsloth wrap.
peft0.14.0LoRA adapter logic. รวม weight 4-bit base + LoRA delta ตอน inference.
trl0.13.0SFTTrainer — supervised fine-tuning loop ที่ Unsloth wrap อีกชั้น.
bitsandbytes0.45.04-bit quantization (load_in_4bit=True). Required สำหรับ QLoRA.
accelerate1.2.0Device placement + dtype management.
datasets3.2.0HF datasets format ที่ SFTTrainer ต้องการ.
optuna4.1.0Hyperparameter optimization. Bayesian search + pruning. แต่ละ trial = nested MLflow run.
mlflow2.19.0Experiment tracking. Log params (flat), metrics (per step), final model artifact. Parent run สำหรับ HPO, nested runs สำหรับแต่ละ trial.
Hard constraint: Models ต้อง ≤ 3B parameters และ ต้อง fit ใน QLoRA 4-bit. ดู ADR-001.

8. Synthetic Data Generation (OpenRouter)

ใช้ teacher LLM สร้าง training data จาก task description (และ seed examples ถ้ามี). ไม่เรียก OpenAI/Anthropic ตรงๆ.

LibraryMin Versionหน้าที่
openai (SDK)1.58.1ใช้กับ base_url=https://openrouter.ai/api/v1. OpenRouter route ต่อไปยัง provider จริง (Claude, GPT, ฯลฯ) โดย API เดียวกัน. ดู ADR-003.

Flow

  1. User POST /datasets/generate ระบุ task type + description + (optional) seed + holdout_size
  2. Celery task generate_synthetic_data เรียก OpenRouter ทีละ batch (JSON mode)
  3. ทุก row ผ่าน Pydantic validator ตาม task type (closed-label / tool-name / param-type)
  4. Dedup (SHA-1 ของ text/question แบบ normalize)
  5. Optional LLM judge filter (rubric 1-5)
  6. Stratified split → parent dataset (train) + child dataset (holdout) ถ้า holdout_size > 0
  7. Upload JSONL ไป MinIO + insert Dataset row + publish progress ผ่าน Redis

12. เทคที่ "ห้ามใช้" และเหตุผล

การ deviate ต้องเปิด ADR ใหม่. ของพวกนี้ถูกตัดสินไปแล้วใน ADR-001 / ADR-003 / ADR-004.

ห้ามใช้ใช้แทนเหตุผล
Weights & Biases / TensorBoardMLflowOne tool, ทำได้ทั้ง tracking + registry, self-hosted (ADR-001)
OpenAI / Anthropic SDK ตรงๆOpenRouter (ผ่าน openai SDK)Provider-agnostic, สลับ teacher model ผ่าน env (ADR-003)
FastAPI BackgroundTasksCeleryLong jobs ต้องอยู่นอก HTTP process, ต้อง retry-able + cancellable (ADR-004)
HF Trainer sync ใน API processCelery workerAPI process ต้อง free สำหรับ HTTP, GPU blocking โดน Celery กัน
vLLM / TGIOllamaGGUF flow ง่ายกว่ามากบน RTX 3060 (12GB)
เพิ่มเติม — Hard constraints (ห้าม violate):
  • Models ≤ 3B parameters และต้อง fit ใน QLoRA 4-bit
  • ไม่มี authentication — PoC scope, endpoint เปิดทั้งหมด
  • ไม่มี frontend code — backend-only, frontend เป็นเพื่อนร่วมทีมทำแยก
  • 3 supported task types เท่านั้น: classification / tool_calling / qa (ADR-005)

13. End-to-End Walkthrough (วงจรการใช้งานจริง)

สมมติเรากำลังจะสร้าง spam classifier — fine-tune SLM ขนาดเล็ก ให้แยก SMS ว่าเป็น spam หรือ ham. ส่วนข้างล่างนี้คือ 7 step ที่ frontend (หรือ developer) จะเรียก พร้อมอธิบายว่า "ภายในระบบเกิดอะไรขึ้น" ในแต่ละ step.

กฎสำคัญของ API: ทุก long-running operation (SDG, training, evaluation, export) จะ return 202 Accepted ทันที พร้อม job_id + websocket_url. Frontend ต้องเปิด WebSocket /ws/jobs/{job_id} เพื่อรับ progress events แบบ realtime. ไม่มี polling.

สร้าง Project (sync, instant)

Project คือ container ของทั้ง workflow. กำหนด task_type ที่นี่และ lock ไว้ตลอด — ทุก dataset/training/eval ภายในต้องเป็น type เดียวกัน.

POST /api/v1/projects
{
  "name": "spam-classifier",
  "description": "Detect spam SMS for Thai telecom",
  "task_type": "classification"
}

→ 201 Created
{ "id": "01HXYZ...", "name": "spam-classifier", "task_type": "classification", ... }
ภายในระบบ:
  • api/routers/projects.py → api/services/projects_service.py
  • SQLAlchemy async insert ลง projects table
  • ไม่มี Celery, ไม่มี WebSocket — เป็น sync HTTP ปกติ

Generate Synthetic Data (async + holdout split)

ตรงนี้คือหัวใจของระบบ. ใช้ teacher LLM (Claude 3.5 Sonnet ผ่าน OpenRouter) สร้าง training data 200 rows + holdout 50 rows.

POST /api/v1/datasets/generate
{
  "project_id": "01HXYZ...",
  "sdg_mode": "description_only",
  "task_description": "Classify Thai SMS as spam or ham",
  "labels": ["spam", "ham"],
  "num_samples": 200,
  "holdout_size": 50
}

→ 202 Accepted
{
  "dataset_id": "ds-parent-uuid",
  "job_id": "celery-task-id",
  "websocket_url": "/ws/jobs/celery-task-id"
}
ภายในระบบ (Celery worker จะทำให้):
  • API process: validate request → insert Dataset row (status=PENDING) → enqueue Celery task generate_synthetic_data → return 202
  • Worker: workers/tasks/data_generation.py ทำต่อ:
    • Build prompt (ai_engine/data_gen/prompts.py) ตาม task_type + mode
    • Loop เรียก OpenRouterClient.create_chat_completion() แบบ batched (tenacity retry on 429/timeout)
    • ทุก row ผ่าน validate_generated_rows() — drop row ที่ label นอก allowlist
    • Deduplicator ตัด duplicate (SHA-1 normalize)
    • Optional: LLM judge filter (rubric 1-5)
    • holdout_split.split_rows() — stratified by label → 200 train + 50 holdout
    • Save train JSONL → MinIO datasets/generated/{parent_id}.jsonl
    • Save holdout JSONL → MinIO + insert child Dataset row (parent_dataset_id = parent_id)
  • Progress: ระหว่างทำ publish sdg_progress ทุก batch ไปยัง Redis channel job:{id}
WebSocket events ที่ frontend จะได้รับ:
sdg_progress sdg_progress ... completed

Final completed.result มี: samples_generated, holdout_samples, holdout_dataset_id, storage_uri, api_calls, duplicate_count, judge_rejected_count ฯลฯ.

{

  "dataset_id": "ds-parent-uuid",   ← ใช้ parent (200 rows) เทรน, ไม่ใช่ holdout

16. ข้อควรระวัง / Common Pitfalls

เก็บจาก lesson learned ใน live runs (Session 12-21).

GPU memory: หลัง training ทุกครั้งต้อง del model; torch.cuda.empty_cache() ใน finally block. ถ้าไม่ทำ → OOM ใน task ถัดไป. (ADR-002 STRICT mode)
Holdout != optional ในทาง quality: ถ้า user POST /evaluations โดยใช้ parent dataset (dataset เดียวกับที่เทรน) → metrics สวยเกินจริง เพราะ Unsloth eval-split 10% มาจากที่นั่นเอง + judge เห็น expected ตรงๆ. UI ควร default ให้ใช้ holdout child เสมอ.
Base model allowlist: ส่ง base_model ที่ไม่อยู่ในรายชื่อ GET /base-models → 400. ห้าม hardcode list ใน FE — เรียก endpoint นี้แล้ว cache เอา.
WebSocket ไม่ปิดเองหลัง completed: Server ไม่ auto-close socket หลังส่ง completed หรือ failed. FE ต้อง close เอง.
training_progress มี "null marker" event: ท้ายแต่ละ epoch worker emit 1 event ที่ train_loss / eval_loss / lr เป็น null ทั้งหมด — ใช้เป็น marker เฉยๆ ไม่ใช่ data point. FE ต้อง skip ก่อน plot.
HPO บน dataset เล็กเกินไป: ถ้า dataset < ~10 rows → eval split ปัดเป็น 0 → ทุก trial fail → "No trials are completed yet". แนะนำ num_samples ≥ 50 สำหรับ HPO.
OPENROUTER_API_KEY: ต้อง set ใน .env ก่อน docker compose up api — ถ้า api container start ก่อน key set จะ load env ไม่เจอ ต้อง docker compose up -d api ซ้ำ.

17. PostgreSQL — Data Flow (เข้า/ออก แต่ละ table)

หลักการ: PostgreSQL เก็บ metadata + pointer + status เท่านั้น — ของหนัก (JSONL, LoRA weights, GGUF, training loss per-step) อยู่ที่ MinIO และ MLflow. ทุก byte ที่หนักกว่า kilobyte ถูก offload ออกไปที่อื่น.

17.1 ER Schema (5 tables + foreign keys)

projects │ 1 │ │ N datasets ─────────< (parent_dataset_id, self-FK สำหรับ holdout child) │ 1 │──────────────────────────────────────────────────────────────────────────────────────────&boxgt; │ N N │ │ training_jobs evaluation_runs │ 1 │ N │ │ │ 1 │ 1 model_artifacts ──────────────────────────────────────────────&boxgt; Legend: │ = FK 1-to-N < = self-reference &boxgt; = end FK

17.2 Data Flow Diagram (sources → tables → consumers)

ฝั่งซ้าย = ใคร INSERT/UPDATE ลง Postgres. ฝั่งขวา = ใคร SELECT ออก. ตรงกลาง = 5 tables.

SOURCES (write) POSTGRESQL CONSUMERS (read) ========================== =================== ========================= API ─ insert (POST /projects) ────&boxgt; projects ────&boxgt; API GET /projects ────&boxgt; ทุก endpoint validate project_id ↓ FK API ─ insert PENDING (generate) ──&boxgt; datasets ────&boxgt; API GET /datasets/{id} Worker ─ UPDATE storage_uri ────&boxgt;| (parent + ────&boxgt; Worker อ่าน storage_uri → ไป MinIO num_samples, | holdout ดึง JSONL จริง (Step 3, 6) generation_metadata | children) Worker ─ INSERT child (holdout) ──&boxgt;| ↓ FK API ─ insert PENDING (POST trainings) &boxgt; training_jobs ──&boxgt; API GET /trainings, /trainings/{id} Worker ─ UPDATE RUNNING ────────&boxgt;| ────&boxgt; API อ่าน mlflow_run_id → ดึง + started_at + mlflow_run_id| loss-history / metrics Worker ─ UPDATE COMPLETED ──────&boxgt;| จาก MLflow (proxy) + best_metric (HPO only) ↓ FK Worker ─ INSERT (lora_adapter_uri) &boxgt; model_artifacts ─&boxgt; API GET /models, /models/{id} Worker ─ UPDATE gguf_uri ──────&boxgt;| ────&boxgt; API resolve UUID → ollama_model_tag + ollama_model_tag | (ใช้ใน /inference/chat/completions) + size_mb ↓ FK API ─ insert PENDING (POST evals) &boxgt; evaluation_runs &boxgt; API GET /evaluations Worker ─ UPDATE COMPLETED ──────&boxgt;| ────&boxgt; API GET /evaluations/{id} + metrics_json (JSONB) + llm_judge_score

17.3 ภายในแต่ละ Table — IN/OUT

projects

top-level container — CRUD ปกติ, ไม่มี async

columns: id, name, description, task_type, created_at, updated_at
▸ IN (write)
  • API insert เมื่อ POST /projects
▸ OUT (read)
  • API GET /projects, GET /projects/{id}
  • ทุก endpoint ที่ validate project_id (cascade ของ Dataset, TrainingJob)

datasets

เก็บทั้ง seed (upload) + sdg (generated) + holdout (child ของ sdg)

columns: id, project_id, name, task_type, source, num_samples, storage_uri → MinIO, size_bytes, generation_metadata (JSONB), parent_dataset_id (self-FK)
▸ IN (write)
  • API insert PENDING (storage_uri=null) ตอน POST /datasets/generate
  • API insert หลัง user upload seed
  • Worker UPDATE เติม storage_uri, num_samples, size_bytes, generation_metadata หลัง SDG เสร็จ
  • Worker INSERT child (parent_dataset_id set) ตอน holdout split
▸ OUT (read)
  • API GET /datasets, GET /datasets/{id}/preview
  • Worker อ่าน storage_uri → ไป MinIO ดึง JSONL จริง ใน Step 3 (training) และ Step 6 (eval)
  • API validate task_type match ก่อน accept training / eval

training_jobs

หนึ่ง fine-tuning run (manual หรือ HPO) — status state-machine

columns: id, project_id, dataset_id, mode, status, celery_task_id (=job_id), base_model, mlflow_run_id, config_json (JSONB), best_metric_value, best_params_json, error_message, started_at, ended_at
▸ IN (write)
  • API insert PENDING + celery_task_id ตอน POST /trainings
  • Worker UPDATE → RUNNING + started_at + mlflow_run_id (ตอนเริ่ม)
  • Worker UPDATE → COMPLETED + ended_at (+ best_metric_value, best_params_json ถ้า HPO)
  • Worker UPDATE → FAILED + error_message (ถ้า exception)
  • API UPDATE → CANCELED (ถ้า user cancel)
▸ OUT (read)
  • API GET /trainings, GET /trainings/{id}
  • API อ่าน mlflow_run_id → ดึง chart data จาก MLflow (proxy ใน /loss-history, /metrics)

model_artifacts

output ของ training ที่สำเร็จ — 1-to-1 กับ training_jobs

columns: id, training_job_id (unique FK), name, base_model, mlflow_run_id, lora_adapter_uri → MinIO, gguf_uri → MinIO, safetensors_uri, size_mb, ollama_model_tag, export_error_message
▸ IN (write)
  • Worker INSERT (lora_adapter_uri) เมื่อ training สำเร็จ
  • Worker UPDATE gguf_uri + size_mb + ollama_model_tag หลัง export + Ollama register
  • Worker UPDATE export_error_message (ถ้า export fail)
▸ OUT (read)
  • API GET /models, GET /models/{id}
  • API resolve UUID → ollama_model_tag ใน POST /inference/chat/completions แล้ว forward ไป Ollama

evaluation_runs

metrics ของ (model_artifact, dataset) pair

columns: id, model_artifact_id, dataset_id, celery_task_id, status, metrics_json (JSONB), llm_judge_score, llm_judge_model, error_message, started_at, ended_at
▸ IN (write)
  • API insert PENDING ตอน POST /evaluations
  • Worker UPDATE → RUNNING + started_at
  • Worker UPDATE → COMPLETED + metrics_json + llm_judge_score + ended_at
▸ OUT (read)
  • API GET /evaluations, GET /evaluations/{id} — FE ใช้แสดงผล metrics + judge score

17.4 สรุปแต่ละ Workflow Step — เขียนอะไรลง Postgres / อ่านอะไรออก

Step 1 (Create Project) IN ─&boxgt; INSERT projects OUT &boxlt;─ (step ถัดไปทุกตัวอ่าน project_id เพื่อ validate) Step 2 (SDG) IN ─&boxgt; INSERT datasets (PENDING, storage_uri=null) <─ จาก API IN ─&boxgt; UPDATE datasets SET storage_uri, num_samples, <─ จาก Worker size_bytes, generation_metadata IN ─&boxgt; INSERT datasets (child, parent_dataset_id=) <─ จาก Worker (holdout) Step 3 (Training) IN ─&boxgt; INSERT training_jobs (PENDING) <─ จาก API IN ─&boxgt; UPDATE training_jobs SET status=RUNNING, <─ จาก Worker mlflow_run_id, started_at IN ─&boxgt; INSERT model_artifacts (lora_adapter_uri) <─ จาก Worker IN ─&boxgt; UPDATE training_jobs SET status=COMPLETED, <─ จาก Worker ended_at (+ best_metric_value ถ้า HPO) OUT &boxlt;─ SELECT mlflow_run_id (สำหรับ chart endpoint) ─&boxgt; ไป MLflow Step 4 (Export GGUF) IN ─&boxgt; UPDATE model_artifacts SET gguf_uri, <─ จาก Worker ollama_model_tag, size_mb Step 5 (Inference / Serve) OUT &boxlt;─ SELECT model_artifacts WHERE id=? ─&boxgt; resolve ollama_model_tag (no INSERT/UPDATE — inference เป็น stateless) Step 6 (Evaluation) IN ─&boxgt; INSERT evaluation_runs (PENDING) <─ จาก API OUT &boxlt;─ SELECT datasets.storage_uri (holdout) ─&boxgt; ไป MinIO ดึง JSONL OUT &boxlt;─ SELECT model_artifacts.ollama_model_tag ─&boxgt; ไป Ollama predict IN ─&boxgt; UPDATE evaluation_runs SET status=COMPLETED, <─ จาก Worker metrics_json Step 7 (LLM Judge — embedded ใน Step 6) IN ─&boxgt; UPDATE evaluation_runs SET <─ จาก Worker llm_judge_score, llm_judge_model
ประเด็นสำคัญ:
  • storage_uri เป็นแค่ pointer — ทุกครั้งที่จะใช้ data จริงต้องไป MinIO เอง
  • celery_task_id = job_id public = WS channel suffix — ตัวเดียวกันหมด, ลิงก์ทุกอย่างเข้าด้วยกัน
  • mlflow_run_id ก็เป็น pointer เหมือนกัน — loss per-step ไม่ได้อยู่ใน Postgres, FE ขอ chart ครั้งไหน API ดึงสด ๆ จาก MLflow
  • 4 JSONB columns (generation_metadata, config_json, metrics_json, best_params_json) เป็น "ตู้รับของยืดหยุ่น" — schema เปลี่ยนได้โดยไม่ต้อง migrate
  • Worker เขียน Postgres ตรงๆ ผ่าน sync session (workers/sync_db.py) ไม่ผ่าน API — process แยก ไม่ block FastAPI event loop
